1. Getting started

ArchToolKit is a set of web pages for architecture work on VMware and multi-cloud estates: reading a VMware inventory, sizing and writing a VMware Cloud Foundation (VCF) 9.1 deployment, generating Terraform and Ansible, editing infrastructure files, and planning application migrations. It runs entirely in your browser. There is no server-side component, no account, and no network call from the pages.

Running it

The pages have to be opened through a small local web server, not by double-clicking the files. Browsers block the pages' code when they are opened straight from disk.

You haveDo this
Node.js 22.6 or newer, on WindowsDouble-click start.bat in the toolkit folder. It builds, finds a free port between 8080 and 8091, starts the server and opens your browser. Options: --dev (rebuild on every change), --port N, --no-open.
Node.js, any systemnpm run build then npm run serve, and open the address it prints. npm run dev does both and rebuilds as files change.
Windows with no Node at allDouble-click start.bat anyway. With no Node on the PATH it serves the built pages with Windows PowerShell instead: localhost only, no admin rights, nothing to install. If a policy blocks scripts, run powershell -NoProfile -ExecutionPolicy Bypass -File tools\serve.ps1. Only --dev needs Node.
Python but no NodeThe built pages are already in the folder. From web\, run python -m http.server 8080 and open http://localhost:8080.
An internal web serverCopy the web folder to it as static files. Nothing else is needed.
Getting it onto another machine: on GitHub, Code → Download ZIP and extract it. The download already contains the built pages, so it runs with nothing but start.bat. To develop on that machine as well, you need Node: use the Node.js .zip download, extract it to a folder of your own, and add that folder to your account's PATH ("Edit environment variables for your account"). Or ask IT; Node.js LTS is often in Company Portal or Software Center. There is no npm install step: the toolkit has no dependencies.

Load, Save, Clear

On the Spec Builder, Terraform and Ansible pages, a strip above the form:

  • Load…: fill the form from a settings file saved earlier (JSON, YAML or TXT).
  • Save: download the form as a settings file, in the format picked beside it: JSON, YAML, or Text (field = value), one answer per line, easy to read in an email and safe to edit in Notepad. All three load back identically.
  • Clear: reset this page's form to its defaults (press twice). Unlike Clear all, it touches nothing else.

Passwords and keys are never saved. A file from another page is refused with a message saying which page it came from. On Terraform and Ansible the file also carries the whole build list, so a stack or a site playbook is one file you keep, share or come back to; Clear empties the list as well as the form.

The build list

On Terraform and Ansible, above the steps. One blueprint writes one thing; a migration or a landing zone is a dozen of them, so the build list assembles them into a single project — a Terraform stack (section 8) or an Ansible site playbook (section 9). Add each piece with Add to build, reorder, edit or remove items, then generate the lot. A field can take a value from what the other items in the list already make, through the ⇢ box beside it.

The cloud is chosen once

The platform picked on Terraform (either tab) or Ansible is shared by both for the rest of the tab. Change it on either and the other follows.

Findings

Checks are reported as findings: error (it will fail or be refused), warning (it will work but probably is not what you want) and info. Most carry what to do about it and where the rule comes from. Figures marked Verified come from Broadcom's API reference, TechDocs or a real deployment spec; Community ones from community sources.

4. VMware Inventory

VMware Inventory is where the estate comes in. Import the RVTools workbook (or its tabs as CSV, or the collector's JSON) once, and the page shows the estate's capacity, clusters, consolidation ratios, VCF 9.1 host readiness, licensing exposure and what stands in the way of moving each VM. Every other page then works from the same estate: sizing fills itself in per cluster, the spec builder takes the management cluster's hosts, DNS, NTP and networks, the Terraform and Ansible generators offer its names and build from its VMs, and Application Migration starts from its servers. Importing the estate

The estate strip is the same on every page (see Things every page shares). With nothing imported it reads No estate loaded and offers Import RVTools…; below it the page says No estate loaded yet.

It accepts, in any mix, in one import:

  • The RVTools workbook (.xlsx) as RVTools writes it (File › Export all to xlsx). Every tab RVTools 4.x writes is read: vInfo, vCPU, vMemory, vDisk, vPartition, vNetwork, vCD, vUSB, vSnapshot, vTools, vSource, vRP, vCluster, vHost, vHBA, vNIC, vSwitch, vPort, dvSwitch, dvPort, vSC_VMK, vDatastore, vMultiPath, vLicense, vFileInfo, vHealth and vMetaData (27 tabs). Tabs are streamed one at a time, so a very large vDisk tab does not have to fit in memory. Tabs that are not RVTools tabs are left alone and listed in an info finding.
  • RVTools tabs saved as CSV, one file per tab. Each file is recognised by its header row, or failing that by its file name (for example export_vHost.csv). Exports older than RVTools 4.x are recognised by looser header checks for vHost, vDatastore, vInfo, dvPort, vNetwork and vCluster. A file that cannot be identified is named in a warning.
  • The collector's JSON from Export-AtkInventory.ps1 (see section 19). Any file ending .json, or whose content starts with {, is read as collector JSON.
  1. Click Import RVTools… and pick one or more .xlsx, .csv or .json files, or drag the files onto the strip.
  2. Watch the status line: Opening <file>…, Reading vDisk (n of m)…, Assembling the estate…, Saving….
  3. When it finishes, the strip reads Estate: <file> — N VMs, N hosts, N clusters, N vCenters, with the collection time when the source carries one, and the cards below fill in.
  4. Use Open on any other page's strip to come back here, Import RVTools… to load a different estate, or Forget to delete it from this browser.

Notes:

  • Each import replaces the stored estate. To combine sources (several vCenters' workbooks, or a workbook and its CSVs), select all the files in the same import.
  • When files are combined, records are matched by vCenter and name (VMs by vCenter and UUID) and the first file's record is kept whole; fields from two files are not merged into one record. Hosts and VMs in a collector file carry no vCenter name, so a host that is in both an RVTools workbook and a collector file is listed twice. Import the collector file on its own when you want its hardware facts.
  • Several vCenters in one RVTools export are kept apart: clusters, hosts and VMs with the same name in two vCenters stay separate.
  • Templates and SRM placeholder VMs are kept and marked. They count toward storage and not toward VMs, vCPU or memory.
  • A raw device mapping is counted once per LUN, in its own figure, not once in every VM that maps it (RVTools' In Use MiB counts it in every VM).
  • Custom attributes defined in vCenter are kept under their own names. Licence keys are cut to their last five characters on import; the rest of the key is never stored.
  • If the file cannot be read, the status line says Could not read that: with the reason.

Moving the VMs

Every workload VM (templates and SRM placeholders excluded) is checked for what stands between it and a move. Severity is about the move, not the VM's health: a blocker stops a live migration as things stand, a caution changes how the move is done, and a note is something the plan should carry.

Four figures at the top:

  • Ready as they are: VMs with nothing, or only notes, for a move to VCF.
  • Need attention: VMs whose worst finding is a caution.
  • Blocked: VMs with at least one blocker.
  • Blocked for a cloud: the same count for a move off vSphere, with how many more need attention.

VCF licensing exposure

VCF 9.1 bills per core with a 16-core minimum per physical CPU. Three figures: Physical cores, Billable cores and Floor penalty (cores paid for that do not exist), with how many hosts are below the floor. When any are, a table lists each host with its cores per CPU and cores wasted. Consolidating onto CPUs of 16 cores or more removes the penalty.

As a VCF fleet

A first-pass sizing of the whole estate as VCF, on defaults: the most common host model in the estate as the target host, each source cluster resized onto it at 4:1 vCPU per core and 90% memory, with 20% growth and N+1, one workload domain per vCenter. The management domain is converged onto an existing cluster when one is named like a management cluster (mgmt, mgt, m01 and similar) with at least three hosts and no RDMs; otherwise it is sized as new hosts.

Four figures: Workload domains (with their clusters), Target hosts (against today's host count), Billable cores (with the target host), and Management domain (Converged or New hosts, with its host count and blocking findings). Two actions:

  • Open in sizing: go to VCF Sizing, where every one of these defaults can be changed.
  • Download sizing input (JSON): saves the plan as vcf-estate-plan.json.

The card is missing when no host has both a core count and memory, or when there are no source clusters.

Findings

The heading shows the number of errors and warnings. The list combines three sets of checks, sorted by severity:

  • From the import: no hosts or VMs imported; VMs without hosts (vHost tab missing); hosts with no core count; no consumed-capacity column (so thin provisioning cannot be measured); RVTools is point-in-time only; the export was collected between 00:00 and 06:00 when estates are idle; VMs mapping raw LUNs; a workbook with no RVTools tabs; tabs not from RVTools; files that could not be identified. For a collector JSON: not valid JSON; not a JSON object; no hosts or VMs; a schema version other than 1.0; whether historical statistics are present.
  • From the estate analysis: licensing floor penalty (info); vCPU:pCPU above 4:1 (warning); allocated memory above physical (warning); more than 30% of provisioned storage unconsumed (info); datastores above 90% used (warning, first five named); hosts on ESX below 8.x (error); hosts below 128 GiB for vSAN ESA (warning); a cluster with mixed CPU models (warning, one per cluster); hosts in maintenance mode (info); no hosts at all (warning).
  • From host readiness: hosts with no NVMe (error); storage detail missing, so ESA cannot be confirmed (warning); hosts with no NIC at 25 GbE (warning); hosts with a blocking issue (error, first five named) or all hosts viable (info); how many checks could not be evaluated (info).

Most findings carry what to do about them and the source of the rule.

Export

Download canonical inventory (JSON) saves the merged estate as atk-inventory.json: every source in one schema, including each VM's disks, NICs and other detail. It is a record you can keep or inspect. Imported again, it is read as a collector file: hosts, VMs, clusters, datastores and networks come back, but RVTools-only detail (VM disks, NICs, CD/USB devices, vCenters, health messages, licences) does not. For a complete estate on another machine, import the original RVTools workbook there.

Typical workflow

  1. Export every vCenter from RVTools (Export all to xlsx) and import all the workbooks together.
  2. Check Source: every vCenter is listed and the tabs you expect were read.
  3. Read Findings for errors, then Consolidation and Clusters for the shape of the estate.
  4. Check VCF 9.1 host readiness. If NVMe or TPM read ?, run the collector and import its JSON to settle them.
  5. Review Moving the VMs and start remediating blockers.
  6. Use Take it further or Open in sizing to carry the estate into VCF Sizing, the spec builder, Application Migration and the generators.

Point-in-time data understates bursty workloads. Size on allocation, or on a 30-day peak from VCF Operations, not on the utilisation in one export.

What it checks

Findings are errors, warnings or info (see section 3), each with a message, the field it concerns, what to do and, usually, a source. The checks cover:

  • host counts below the minimum or the recommended count, and the profile not being available in the chosen release (HA-Small on 9.1.0);
  • vSAN: fewer than three hosts, three hosts that cannot rebuild, a policy that needs more hosts, ESA on 10 GbE, ESA host RAM;
  • CPU above the target ratio, memory insufficient or high, storage insufficient;
  • stretched clusters: inter-AZ bandwidth and round trip, uneven host split; two-node proposed as management;
  • memory tiering: ratio, active memory, NVMe shared with vSAN, DRAM for HA;
  • VCF Automation on hosts too small, on an additional instance, or at an unconfirmed size; edge node counts and Small edges (lab only);
  • add-ons: log replica limits and retention, VCF Operations for Networks size and cluster, Avi controller count and size, Protection and Recovery scale-out, services that belong to the first instance only;
  • workload domains: vCenter too small for the hosts and VMs, shared NSX with no domain to provide it, stretched workload clusters without a stretched management domain, clusters that cannot fit, two-node clusters (unconfirmed);
  • licensing: per-CPU core floor, vSAN add-on capacity, VCF Edge site and core limits;
  • a new management domain on NFS or FC (supported; the datastore must exist first), a recovery site whose storage is full, and fleet figures Broadcom does not publish.

What the validator checks

The 9.1 validator runs on every build and on imported specifications. It checks:

  • required keys, unknown keys (with a suggested spelling), value types, enumerations and their case, and keys removed in 9.1;
  • the workflow type against the existing components and blocks each scenario needs (including the Identity Broker and fleet-only services on a secondary instance);
  • SDDC ID, instance name, hostnames, FQDNs (duplicates, IPs used as names, vCenter hostname length), DNS and NTP servers (including a single NTP server);
  • networks: subnets, masks, gateways, VLANs, MTUs, ranges, TEP ranges, management services pool size and address family, IPv6 prefixes and SLAAC;
  • switches, port group and LAG name lengths, teaming without an active uplink, TEP-less and VLAN-backed VPC consistency and version, DTGW blocks;
  • password length rules for SDDC Manager and NSX, thumbprint format (SHA1 flagged), FTT range, VCF Operations node count and xsmall with HA, and existing-component blocks carrying extra fields.

Registry module blueprints and What this will create

A module blueprint writes one module block. The module's version is pinned to its minor line (~> major.minor) at the version the module catalog was read from, and every input on the form is checked against that version's own variables by the toolkit's tests. Only inputs you fill in are written; an empty field means the module's default. Where the module takes tags, ManagedBy = "terraform" and System = <name> are added. The root terraform block names the provider without pinning its version (the module declares what it works with); commit .terraform.lock.hcl after init to hold the version it chose.

The form has two parts:

  • The headline inputs, plus any input the module requires that the headline did not list.
  • A collapsed section, All N inputs of <source>, with every other input in the module's order, each with its type, its default and the module's own description. A yes/no input left blank shows Module default (…).

Under the files, What this will create lists every resource the module can make, each marked Created, Not created or Depends, worked out from your answers the way Terraform would evaluate the module's own conditions. The heading counts them (N resources, M depending on values outside the form, of T the module can make). A Depends row shows the condition it could not decide (it involves a function or another resource's attribute), rather than guessing.

Single-resource blueprints

One blueprint per resource type, made from the provider's own schema. The description says how many arguments it takes (required, optional, nested blocks) and which provider version the schema came from.

  • Required arguments are at the top; optional ones in a collapsed section; each nested block has a tick box, and its fields (in a section named Block: …) appear when it is ticked.
  • A yes/no argument is a true/false dropdown, with (provider default) when it is optional. An argument with a documented set of values is a dropdown you can type into.
  • A required argument left empty becomes a variable rather than a guess, so the file plans once you supply it. Where the provider needs one of several arguments, the hint says so, and if you set none the first becomes a variable.
  • Deprecated arguments and computed-only ones are left out.
  • The Provider connection section holds the provider's own settings (endpoint, user, region and so on). Credentials are never fields here.
  • On AWS, Azure, Google Cloud and OCI the schema is loaded when you pick the resource; the form says Loading every argument this resource takes… until it arrives. If it cannot be loaded, Step 3 shows an error saying so.

One blueprint writes one thing; a landing zone is a dozen of them. The Build list card above the steps assembles them into one root module.

Saving, loading and clearing

The strip above the steps:

  • Load settings…: fill the form from a file saved earlier (JSON, YAML or TXT). Fields the blueprint no longer has are skipped and listed.
  • Save settings: download the platform, the blueprint, its answers and the whole build list, in the format picked beside it (JSON, YAML or Text (field = value)). The file is the form's values, not the generated output.
  • Clear: press twice. Puts the form back to the first blueprint and empties the build list.

Passwords and keys are not saved. A file saved from another page is refused with a message saying which page it came from.

Credentials

  • No credential is written into any generated file. The cloud providers read theirs from the environment, a profile or a CLI login (for example ARM_SUBSCRIPTION_ID and the Azure CLI login for Azure).
  • The VMware, Active Directory and DNS providers take their password or token from a sensitive variable (vsphere_password, sddc_manager_password, nsx_password, avi_password, vra_refresh_token, vcd_password, ad_password, dns_tsig_secret and so on). Set it as TF_VAR_<name>; the VCF landing zone for a cluster blueprint instead expects VSPHERE_USER and VSPHERE_PASSWORD.
  • In the single-resource and scenario blueprints, a sensitive argument is never a text box: it is a var. reference to a variable declared sensitive.
  • A sensitive value is kept out of plan output but is still written to state, so protect the state file too.

Checks

  • Every resource type the blueprints write is checked, by the toolkit's own tests, against the committed provider catalog (AWS 6.66.0, AzureRM 5.7.0, Google 8.4.0, OCI 9.3.0, vSphere 2.17.1, VCF 0.18.2, NSX 3.12.1, Avi 32.1.3, VCF Automation 0.17.4, Cloud Director 3.14.2, fetched 27 September 2026), so a resource renamed in a provider release is caught before it reaches you rather than at terraform plan.
  • Every module input is checked the same way against the module catalog (43 registry modules, read from each module's own variables at the pinned version).
  • At generate time, Findings reports what is wrong with the values you gave: a number field holding text, a required block that has to be written by hand, an estate problem, and the stack warnings above.

Typical workflow

  1. Import the estate if you are moving one; pick the platform.
  2. Check the Map tab if you are not sure which resource does the job.
  3. Fill in each blueprint and Add to build, linking later items to earlier ones with ⇢.
  4. Generate stack, read the Findings and the Reference panel, and Save settings so you can come back to it.
  5. Download as .zip, fill in terraform.tfvars, set credentials in the environment, then terraform init and terraform apply (with terraform plan first if you want a dry run).

Applying it with Ansible

  1. Put the real devices and addresses in inventory/hosts.yml.
  2. Put the credentials in a vault: ansible-vault create group_vars/all/vault.yml, with the vault_* variables the inventory names.
  3. ansible-galaxy collection install -r requirements.yml
  4. ansible-playbook -i inventory <name>.yml --diff --limit <device> — it applies. Add --check first if you want a dry run; it is the closest a network device has to a plan.

On the CLI platforms the playbook saves the configuration only when it changed (save_when: changed); on IOS-XR and Junos it commits with the change title as the comment. Building a whole change

A real change is rarely one command: the VLAN before the trunk that carries it, the pool before the virtual server, the interface before the rule that uses its zone. The build list assembles the steps in order.

  1. Pick a change, fill it in, give it a name, and press Add to change.
  2. Repeat for each step, on any platform. Each row has ↑ / ↓, Edit (the button then reads Update in the list) and Remove.
  3. In a text field, the ⇢ box offers the names of the earlier steps.
  4. Fill in Name for this change and press Generate change. Clear list empties it; Network calculator opens the subnet calculator (IPv4 and IPv6).

01-<step>.cfg, 02-<step>.cfg, …One file per step, in order, each with its own capture, verify and back-out (where the platform allows comments).

The full configuration is every step for that device merged, not stacked: two steps that touch the same interface become one interface block carrying everything they set, repeated lines are dropped, and the whole thing is in the order the platform's own running configuration uses (system and management, VLANs, interfaces, spanning tree, routing, policy). PAN-OS is written interfaces and zones, objects, NAT, then security rules, ending with the commit; FortiOS system, routing, addresses, then policies. For F5 it is one AS3 declaration per tenant — the only correct way to combine them, because AS3 replaces a tenant wholesale — and the tmsh onboarding steps stay in their own step files, to run first.

Step files and the full configuration are for different jobs. The step files carry the checks and the back-out and are what a change window needs. The full configuration carries neither — it is the destination, not the journey — and is what a device build needs. It is only as complete as the steps you added: include the management baseline (hostname, NTP, logging) and spanning tree if you are building a device from scratch.

Two platforms in one change stay in separate files, because that is two sessions on two devices. Each step is rebuilt from its blueprint when you generate, so an item added earlier reflects the current rules.

Checks and findings

  • The impact of the change (for a build list, the worst impact of its steps), as a warning when it is brief or outage.
  • A change with no back-out written.
  • Answers the change cannot use, checked per platform: an invalid address or prefix, a next hop of the wrong address family, no interfaces, VLANs or pool members given, and similar. Some warn about a risky choice rather than refuse it, such as a loopback mask other than /32 or an F5 declaration that references a certificate.
  • Playbook module names that do not exist in the catalog (error), or whose collection is not catalogued (warning).
  • For a build list: a step whose change is no longer on the page, two steps with the same name, a step that could not be built, an FMC step whose operations are not valid JSON, an F5 step that is not a readable declaration, and two F5 steps defining the same application.

The page shows errors and warnings only. Every generated file is a draft: diff it against the running configuration before you apply it.

Changes handed over from a migration plan

A migration plan can send device changes to this page, listed in a banner with an Open button for each. The migration pages are being rebuilt.

Typical workflow

  1. Add the steps in the order they must be applied, across all the devices the change touches.
  2. Name the change and generate it. Read the impact and fix any errors or warnings.
  3. Attach change-record.md to the ticket and get it signed off.
  4. In the window: run the capture commands, apply each step file by hand or run apply.yml with --limit, verify after each step, then save or commit.
  5. If it goes wrong, use the back-out from the record, last step first.

16. VCF Operations content

VCF Ops content reads what is configured in a VCF Operations instance (9.x, or the 8.x releases before it) from its export, and shows all of it at once, cross-referenced. 19. The inventory collector

tools\collector\Export-AtkInventory.ps1 is a read-only PowerCLI script that collects one vCenter's estate into a JSON file for VMware Inventory. It exists for the hardware facts VCF 9.1 readiness depends on that an RVTools export does not carry: which storage devices are NVMe (vSAN ESA needs them) and whether each host has a TPM. It also records physical NIC link speeds, VMkernel adapters and, optionally, historical CPU and memory use. Run it when the host readiness card shows ? for NVMe or TPM. The script ships in the repository's tools\collector folder; it is not a page of the toolkit.

Console warnings

Before it finishes, the script prints, where they apply:

  • N host(s) report no NVMe devices; vSAN ESA requires NVMe.
  • N host(s) have no NIC at 25GbE or above; 25GbE is recommended for vSAN ESA.
  • N host(s) run ESX below 8.0 and cannot be converged into VCF 9.1 as they are.

What the toolkit does with the file

  • The host readiness checks for NVMe devices and TPM can be evaluated, as well as NIC speed and redundancy.
  • Import findings report whether historical statistics are present. The toolkit only notes their presence: the average and peak figures are in the file but are not used in sizing. Size bursty workloads on a peak from VCF Operations.
  • A file declaring a schema version other than 1.0 is still read, with an info finding; unknown fields are ignored. A file that is not valid JSON, or has no hosts or VMs, raises a finding.
  • The Source card shows the vCenter name as the label; the vCenter version table and rows-per-tab line are RVTools-only.

Notes and limits

  • One vCenter per run. Hosts and VMs in the file carry no vCenter name, so two files from vCenters with the same host or VM names collapse into one record when imported together.
  • Combined with an RVTools workbook in the same import, a host that is in both is listed twice (see Importing the estate). Import the collector file on its own when you want its hardware facts.
  • It does not collect VM disks, NIC adapter types, CD/USB devices, DRS rules, vApps, custom attributes, templates, health messages or licences, so most of the Moving the VMs checks need the RVTools workbook.
  • Despite the script's own help text, it does not record the boot device or NIC firmware.
  • TPM is taken from the host's reported TPM support.
  • It turns off certificate checking and CEIP participation for its own PowerCLI session only; nothing persists. It disconnects from vCenter when it ends, including on error.
  • It writes one file and sends nothing anywhere. The file describes a real estate; keep it where you keep the RVTools exports.

20. Keeping catalogs current

The lists the toolkit checks against are stored in the toolkit so it works offline. Refreshing them is the only thing that uses the network, and only to read. Each finding says how old its catalog is and warns after 90 days.

One update for everything: update.bat

update.bat refreshes every catalog, checks everything the toolkit generates with the real tools, rebuilds the pages and runs the tests, then commits and pushes — only if every step passed. Run it from the toolkit's folder in Command Prompt, or with .\update.bat in PowerShell.

How to run it

  1. Open Command Prompt in the toolkit's folder (or PowerShell, and type .\ before the name).
  2. Run update.bat, then press Enter for every area or type the letters you want, e.g. N S V, and answer Y to start.
  3. Or run it unattended: update.bat all /yes (or letters, e.g. update.bat NSV /yes) picks the areas, starts at once, and commits and pushes only if everything passed. Double-clicking airunupdate.bat does the same for every area.
  4. Read the summary at the end: every step is listed as OK or FAILED. If anything failed, nothing is committed, and what the steps rewrote stays in the working copy.

What is current is skipped

The update remembers what has passed, so running it again does only what is left:

  • A download that passed in the last 20 hours is current and is skipped.
  • A check (rule discovery, validation, lint) is current while nothing it reads has changed since it last passed — the blueprints, the tool that checks them, and the installed tool versions.
  • A step that failed is never recorded as passed, so it always runs again.
  • The rebuild and the tests always run.

So after a run with failures, run it again as it is: only the failed steps and whatever depends on them run. /force (e.g. update.bat all /yes /force) runs every step regardless. Current steps show in the summary as current, skipped.

Everything stays in the toolkit's folder

What the update downloads, caches and builds is kept in .work\ inside the toolkit's folder, found from wherever the folder is: nothing is written to a home directory, and no drive letter is fixed, so the folder can be moved or carried whole. Deleting .work\ removes all of it; the next run puts it back.

Protections built in

  • Memory: terraform validate checks 40 blueprints at a time and stops the provider processes each round leaves behind, so memory stays flat (ARCHTOOLKIT_TF_BATCH changes the batch size).
  • Busy files and rate limits: if a provider file is still held by a closing process, terraform init waits and tries again (up to four times); if the Terraform Registry rate-limits, it waits and tries again (up to five times). After that the step fails normally — nothing loops forever.
  • A download that fails leaves that catalog as it was; a registry module that cannot be fetched keeps its previous entry.
  • A check that cannot run (for example a crashed linter) counts as a failure, never as a pass.

21. Common workflows

From an RVTools export to a VCF deployment spec

  1. VMware Inventory: import the RVTools .xlsx (and the collector JSON if you have it). Read the readiness and blockers.
  2. VCF Sizing: in From your estate, choose the management domain, host profile and domain split. Check the verdict.
  3. Continue in the spec builder: check the prefilled hosts and networks, choose the scenario, name the components, add host passwords. Save the settings.
  4. Download the SddcSpec, then validate it on the live installer.

Change a deployed VCF spec

  1. Data Editor: open the installer export (VCF-deployment-spec-….json).
  2. Edit fields in the form, or use Find and replace for a new subnet or domain. Watch the checks.
  3. Download, or Download without secrets to share it.

Rehost a cluster to a cloud

  1. Import the estate; on the inventory page, fix or note the blocked VMs.
  2. Terraform: Rehost a cluster's VMs for the chosen cloud; Ansible: the inventory and before/after playbooks.

Build a landing zone as one project

  1. Terraform: add each piece to the build list — network first, then what sits on it. Use the ⇢ box to point each item at what the earlier ones create rather than typing ids.
  2. Name the stack, Generate stack, and download the files into one folder. terraform init, validate, plan.
  3. Ansible: build the matching site playbook the same way, for what has to be configured once the machines exist.
  4. Save both lists. That file is the design: load it to change one value and generate again.

23. Known limits

  • The spec builder's checks follow the documented 9.1 schema; the live VCF Installer's validation is the authority.
  • A deployment spec cannot yet be loaded into the spec builder's form; edit it in the Data Editor instead.
  • RVTools has no NVMe or NIC-speed data; those readiness columns show ? unless the collector's JSON is imported too.
  • Editing YAML in the Data Editor's form drops comments; the Text view keeps them.
  • In a Terraform stack, a resource offers only its .id to other items, because that is the one attribute every resource has. Module items offer their real outputs. Anything else you write yourself.
  • An Ansible site playbook shares an answer only when two playbooks give it identically; anything named like a password is left out of group_vars/all.yml on purpose.
  • Network changes are written for the platforms listed and checked for structure, not simulated. Diff every one against the running configuration before it is applied.
  • The network vendor Ansible collections are unpinned and un-catalogued until npm run ansible:update runs on a connected machine.
  • Checks confirm names, structure and references. They do not confirm that a deployment will succeed in your environment.
