1. Getting started

ArchToolKit is a set of web pages for architecture work on VMware and multi-cloud estates: reading a VMware inventory, sizing and writing a VMware Cloud Foundation (VCF) 9.1 deployment, generating Terraform and Ansible, editing infrastructure files, and planning application migrations. It runs entirely in your browser. There is no server-side component, no account, and no network call from the pages.

Running it

The pages have to be opened through a small local web server, not by double-clicking the files. Browsers block the pages' code when they are opened straight from disk.

You haveDo this
Node.js 22.6 or newer, on WindowsDouble-click start.bat in the toolkit folder. It builds, finds a free port between 8080 and 8091, starts the server and opens your browser. Options: --dev (rebuild on every change), --port N, --no-open.
Node.js, any systemnpm run build then npm run serve, and open the address it prints. npm run dev does both and rebuilds as files change.
Windows with no Node at allDouble-click start.bat anyway. With no Node on the PATH it serves the built pages with Windows PowerShell instead: localhost only, no admin rights, nothing to install. If a policy blocks scripts, run powershell -NoProfile -ExecutionPolicy Bypass -File tools\serve.ps1. Only --dev needs Node.
Python but no NodeThe built pages are already in the folder. From web\, run python -m http.server 8080 and open http://localhost:8080.
An internal web serverCopy the web folder to it as static files. Nothing else is needed.
Getting it onto another machine: on GitHub, Code → Download ZIP and extract it. The download already contains the built pages, so it runs with nothing but start.bat. To develop on that machine as well, you need Node: use the Node.js .zip download, extract it to a folder of your own, and add that folder to your account's PATH ("Edit environment variables for your account"). Or ask IT; Node.js LTS is often in Company Portal or Software Center. There is no npm install step: the toolkit has no dependencies.

Clear all (top right, red)

Empties the whole toolkit in this browser: the imported estate, everything passed between pages, every page's saved state, and whatever the page is showing. Press it once to arm it (it reads Click again to clear everything), then again within five seconds. It clears every page, not just the one you are on, because the pages feed each other: clearing one page alone would be refilled from the estate by the next.

The estate strip

Under the heading of most pages. With nothing imported it reads No estate loaded and offers Import RVTools… (you can also drag files onto it). Once imported it shows the source, VM, host, cluster and vCenter counts, with:

  • Open: go to the inventory page.
  • Import RVTools…: replace the estate.
  • Forget: delete the estate from this browser.

It accepts an RVTools .xlsx as RVTools wrote it, individual RVTools tabs saved as .csv, the collector's .json, or several of these at once (they are merged).

Load, Save, Clear

On the Spec Builder, Terraform and Ansible pages, a strip above the form:

  • Load…: fill the form from a settings file saved earlier (JSON, YAML or TXT).
  • Save: download the form as a settings file, in the format picked beside it: JSON, YAML, or Text (field = value), one answer per line, easy to read in an email and safe to edit in Notepad. All three load back identically.
  • Clear: reset this page's form to its defaults (press twice). Unlike Clear all, it touches nothing else.

Passwords and keys are never saved. A file from another page is refused with a message saying which page it came from. On Terraform and Ansible the file also carries the whole build list, so a stack or a site playbook is one file you keep, share or come back to; Clear empties the list as well as the form.

The build list

On Terraform and Ansible, above the steps. One blueprint writes one thing; a migration or a landing zone is a dozen of them, so the build list assembles them into a single project — a Terraform stack (section 8) or an Ansible site playbook (section 9). Add each piece with Add to build, reorder, edit or remove items, then generate the lot. A field can take a value from what the other items in the list already make, through the ⇢ box beside it.

The cloud is chosen once

The platform picked on the Multi-Cloud wizard, Terraform (either tab) or Ansible is shared by all three for the rest of the tab. Change it on any of them and the others follow.

Findings

Checks are reported as findings: error (it will fail or be refused), warning (it will work but probably is not what you want) and info. Most carry what to do about it and where the rule comes from. Figures marked Verified come from Broadcom's API reference, TechDocs or a real deployment spec; Community ones from community sources.

4. VMware Inventory

Import once; every other page then works from it.

What it reads

Every tab RVTools 4.x writes: vInfo, vCPU, vMemory, vDisk, vPartition, vNetwork, vCD, vUSB, vSnapshot, vTools, vSource, vRP, vCluster, vHost, vHBA, vNIC, vSwitch, vPort, dvSwitch, dvPort, vSC_VMK, vDatastore, vMultiPath, vLicense, vFileInfo, vHealth and vMetaData, across any number of vCenters. The collector's JSON adds what RVTools does not capture, such as NVMe devices and NIC speeds.

What it shows

  • Estate: hosts, VMs, physical cores and sockets, physical and allocated memory.
  • Take it further: buttons to size VCF, decide where it goes, and generate Terraform or Ansible from it.
  • Source: the vCenters, their versions and collection times, and rows read per tab.
  • Consolidation: vCPU:pCPU (warns above 4:1), memory commitment (amber above 80%, red above 100%), provisioned vs consumed storage, the thin-provisioning gap, RDMs.
  • Clusters: per cluster hosts, VMs, cores, memory, vCPU, vRAM, storage, ratios and CPU models (mixed models flagged).
  • Moving the VMs: every VM sorted into Ready as they are, Need attention, Blocked and Blocked for a cloud, with the reason, what to do, and example VMs.
    • Blockers: disconnected, orphaned or inaccessible VMs; physical-mode RDMs; disks shared between VMs; PCI passthrough.
    • Cautions: virtual-mode RDMs, USB, connected CD/DVD, Fault Tolerance, high latency sensitivity, snapshots, disks needing consolidation, VMware Tools not running, guest OS past support.
    • Notes: independent disks, old virtual hardware, E1000 NICs, large VMs, DRS rules, vApps, SRM protection, BIOS firmware, powered off over 90 days.
  • Health and licences: RVTools health messages and licence use (keys shown by their last five characters only).
  • VCF 9.1 host readiness: per host, ESX version (8.0 U3a minimum), memory (128 GiB for vSAN ESA), NVMe, NIC speed (25 GbE), NIC redundancy, cores per CPU (16) and TPM, with ✓ ✗ ! and ? (? means the source does not have that fact).
  • VCF licensing exposure: billable cores under the 16-cores-per-CPU minimum, and the hosts paying for cores they do not have.
  • As a VCF fleet: a first-pass sizing on default assumptions, with Open in sizing and Download sizing input (JSON).
  • Findings: overcommit, full datastores, ESX too old to converge, mixed CPUs, hosts in maintenance mode and more.

Download canonical inventory (JSON) saves the merged estate as atk-inventory.json, which can be imported again later on any machine.

5. VCF Sizing

Inputs on the left; results recalculate on every change.

From your estate

With an estate imported, a panel above the form sizes it for you. Choose:

  • the management domain: new hosts, or converge an existing cluster (one that looks like management is suggested);
  • the target host profile, raw vSAN capacity per host, how to split workload domains (per vCenter, per datacenter, or one);
  • vCPU per core (default 4:1), memory to use (90%), growth (20%), storage basis (consumed or provisioned), workload storage type, whether powered-off VMs count, and which source clusters are in scope.

It shows a table per domain and cluster with the hosts needed and what set the number (CPU, memory, storage or the minimum).

The form

  • Deployment: path (greenfield, converge to management domain, import as workload domain), profile, instances in the fleet, management hosts, topology (standard, stretched, two-node) and principal storage (vSAN ESA, vSAN OSA, NFS v3, VMFS on FC).
  • Per-host hardware: sockets, cores, hyperthreading, RAM, raw storage, NICs.
  • Tenant workload: vCPU, RAM and capacity to host.
  • Options: VCF Automation and size, NSX Edge cluster, edge size and nodes, N+1, target vCPU:pCPU.

6. VCF Spec Builder

Writes the complete VCF 9.1 deployment specification (SddcSpec) the VCF Installer takes, including the parts other builders leave out: vspClusterSpec, fleet services, VPC/DTGW, LACP and dual-stack.

How it fills itself in

From your sizing (Prefilled from your sizing) or, with only an estate imported, from the estate sized on default settings (Prefilled from your estate): hosts, DNS, NTP, domain, and the management, vMotion and vSAN networks. Check them, then name the components.

The form

  • Instance: SDDC ID, instance name, domain suffix, name prefix, target version, and the deployment scenario, one of Broadcom's eight: new VCF fleet, new VCF instance, deferred components, converge to a new fleet, converge to a new instance, new vSphere Foundation, converge to VVF, and management services plus license server for VVF.
  • Hosts, Services (DNS, NTP), Networks (management, VM management, vMotion, vSAN, host TEP).
  • Fleet-level components: management network model (shared VLAN, dedicated VLAN, with NSX overlay, with stretched overlay), fleet network, pool name, services runtime CIDR, dual stack.
  • Storage and scale: storage type and its details (vSAN options, NFS servers and path, FC datastore names), FTT, HA profile, appliance sizes, EVC, datacenter and cluster names.
  • Switching and NSX: vDS profile and MTU, TEP-less (9.1.1+), LACP, VPC with distributed transit gateway.
  • Components: certificate mode, CEIP, which of Operations, Automation, management services and Identity Broker to include (the scenario fixes some), reusing an existing vCenter and other components (brownfield), and Redact secrets in output.
  • ESX hosts: hostname, root password and thumbprints per host; Add host, Regenerate from name base. Without thumbprints, the spec skips thumbprint validation.

Output

The status (Valid, Review, Invalid), the generated JSON, and findings from the 9.1 validator. Buttons: Download SddcSpec, Edit as JSON (opens it in the Data Editor) and Copy JSON.

Validate an existing specification at the bottom checks a spec made anywhere else. Specs written for 9.0 are rejected, because they reference the fleet management appliance 9.1 removed.

Load / Save / Clear keep the builder's settings in a file (see section 3). A deployment spec itself cannot be loaded into the form; open it in the Data Editor instead.

This page checks every documented rule it knows. Before deploying, validate on the live installer with POST /v1/sddcs/validations; that check is authoritative, this one is not.

8. Terraform generator

  1. Step 1: pick the Platform and the Blueprint.
  2. Step 2: fill in the parameters. Dropdowns you can type into have Other — type a value…. Registry modules keep their less common inputs in collapsed, searchable sections. Press Generate Terraform (HCL) for this one thing, or Add to build to put it in the build list and generate the whole stack later.
  3. Step 3: the generated files, each with Copy and Download, and Download all as one file. For a registry module, What this will create lists each resource as Created, Not created or Depends. Save the result as main.tf and run terraform init and terraform plan.

Building a whole stack

One blueprint writes one thing; a migration or a landing zone is a dozen of them. The Build list above the steps assembles them into one project:

  1. Pick a blueprint, fill it in, name it in Module / file label, and press Add to build instead of Generate.
  2. Repeat for each piece. In any text field, the ⇢ box beside it offers what the items already in the list create — a VPC's id, a module's outputs — so the next item references them instead of a typed-in id.
  3. Name the stack and press Generate stack.

What comes out is a Terraform root module, ready for terraform init:

10. Terraform › the Map tab

A reference for AWS, Azure, Google Cloud and OCI: for each domain (identity, networking, compute, storage, databases, security, landing-zone patterns), which Terraform resources do the job and the pattern around them, with examples. Every resource name is checked against the provider catalog; one renamed since the map was written is marked, with the closest current name in the Findings card.

It answers a different question from the generator — what should I use for this? rather than write it for me — so it is the second tab on the Terraform page rather than a separate entry in the menu: a reference you have to navigate to is a reference nobody opens. The old terraform-map.html address redirects to it, and the rows that talk about what you have just generated also appear under the generator's output.

11. Multi-Cloud wizard

Choose the cloud once in Designing for (Azure, AWS, Google Cloud, OCI), then four steps:

  1. Initiative & basics: type (new service, change, maintenance, migration), name, architecture, traffic, latency, team strengths.
  2. Path details & data: data pattern and sensitivity, geography, integration, source environment, 7R approach, tooling, compliance; plus questions for the initiative type chosen.
  3. Non-functional, security & migration tooling: criticality, uptime, RTO, RPO, ops maturity, security baseline, identity, secrets, data protection, perimeter, F5 usage, security operations.
  4. Sizing & environments: users, requests per second, data volume, ingest, retention, environments, non-prod scale, regions.

Missing answers are pointed out but never stop you. Generate recommendation (or Finish) produces eleven sections: compute, data and storage, integration, operations and governance, security and network, controls and cyber checklist, migration focus, DR, assumptions and gaps, sizing footprint, and an implementation playbook. Full view, Print (or save as PDF) and Save as Word.

With an estate imported, Answer from the estate fills in what the inventory can answer (the migration approach, data volume, environments, regions and a description of the estate) for the whole estate or one cluster. Criticality, uptime, sensitivity and deadlines stay yours.

12. Application Migration and Portfolio

One page for both halves of the job: evaluating an application, and holding the portfolio of everything evaluated so far. They used to be two pages that only met through an exported file, so the dashboard was always out of date. Evaluating an application now adds or replaces its row straight away, and the old portfolio address redirects to the Portfolio tab.

The tabs

Two ways to apply it

Every change generates both. The configuration file is what you paste into a session or hand to whoever has the console. The playbook applies the same change to many devices, and it is generated for a dry run first — --check --diff is the closest a network device has to a plan. The two come from one structure, so they cannot say different things. Cisco, Arista, Juniper and Aruba changes push through the platform's *_config module (Junos and IOS-XR commit with a comment); FMC changes run one fmc_configuration task per API operation; PAN-OS, FortiOS and F5 use their own object modules (panos_security_rule, fortios_firewall_policy, bigip_as3_deploy), and PAN-OS changes include the commit.

No credentials, anywhere. Enable secrets, SNMPv3 keys, BGP session passwords and API tokens are written as <REQUIRED> in configuration and as vault variables in playbooks. The generated inventory says which variables each platform expects. An F5 declaration references a certificate that already exists on the device; none is created or uploaded.

Building a whole change

Add to change collects steps in order — the VLAN before the trunk that carries it, the pool before the virtual server, the interface before the rule that uses its zone. Generating the change writes:

  • one numbered configuration file per step, each with its own capture, verify and back-out;
  • full-<platform>.cfg — the complete configuration for that device: every step merged, not stacked. Two steps that touch the same interface become one interface block carrying everything they set, repeated lines are dropped, and the whole thing is written in the order the platform's own running configuration uses (system, management, VLANs, interfaces, spanning tree, routing, policy). It is what you paste into a device you are building, rather than one you are changing. For F5 it is one AS3 declaration per tenant, which is the only correct way to combine them: AS3 replaces a tenant wholesale, so two declarations for one tenant would delete each other. For PAN-OS it ends with the commit;
  • apply.yml, the same steps as one playbook, plus requirements.yml and an inventory/hosts.yml with the connection variables;
  • change-record.md — the pre-checks, every step with its verification, the back-out in reverse order, and a sign-off table;
  • README.md, which says how to apply it both ways.

Two platforms in one change stay in separate files, because that is two sessions on two devices. The back-out reverses: the last thing built is the first thing removed.

Per-step files and the full configuration are for different jobs. The step files carry the checks and the back-out and are what a change window needs. The full configuration carries neither — it is the destination, not the journey — and is what a build needs. Both are generated every time; use the one that matches what you are doing. When a full configuration is missing something a build should have (a hostname, NTP, spanning tree), the page says so rather than pretending it is complete.
Most changes also generate a playbook. A few have no Ansible module at all — PAN-OS log forwarding, zone protection and decryption, for instance — and those say so in their findings rather than quietly producing nothing.
The vendor Ansible collections (cisco.ios, paloaltonetworks.panos, fortinet.fortios, f5networks.f5_modules and the rest) were added in a build with no access to Ansible Galaxy, so their versions are not pinned and their module names are not yet catalog-checked. 15. Splunk

Splunk writes deployable apps: the conf files, an app.conf so it is a real app, the metadata/default.meta that makes its objects visible to anyone, and a deployment note.

Why the tier is the first question

The platform picker on this page is the Splunk tier — search head, indexer, forwarder, heavy forwarder, management, edge, Cloud or an add-on that spans them — rather than a cloud, because that is the setting that decides whether anything works. A props.conf deployed to a search head does not parse data arriving from a forwarder. The app deploys, the file is read, and nothing happens. There is no error anywhere, and the symptom appears weeks later as events with the wrong timestamp.

TierWhat belongs there
Search headSearch-time only: saved searches, alerts, dashboards, macros, lookups, tags and data models. Index-time settings here do nothing, silently.
IndexerIndex-time: indexes and retention, line breaking, timestamp recognition, routing and masking. The only tier where those take effect for data arriving over a forwarder.
ForwarderCollection and delivery: what to read, what to listen on, where to send it.

17. Automation and Operations

Automation and Operations writes the automations the rest of the toolkit implies: the notification rule that closes the gap the VCF Ops content page keeps finding, the scheduled reclamation, the cloud template people can request, the fleet-wide tag standard. Five targets, which in VCF 9.1 are capabilities of one platform rather than separate products — VCF Operations, VCF Operations for Networks, VCF Operations for Logs, VCF Automation, and fleet management.

Why an automation is not a script

A script runs when somebody runs it, and a person is there to read the output. An automation runs because something happened — an alert fired, a schedule came round, a request was approved — and nobody is watching. It acts on production at three in the morning, on whatever its scope matched that night. So every generated automation carries the same six answers in its README, in the same order:

QuestionWhy it is there
TriggerWhat starts it, and how often it can fire at worst — which is not how often you expect it to.
ScopeWhat it may touch, and every indirection that decides it. An action inherits its scope from an alert, the alert from a policy, the policy from a custom group, and the group from a rule somebody wrote a year ago. Four steps between “power off idle VMs” and which VMs that is tonight.
GuardrailsWhat has to be true before it acts: a cap on objects per run, an exclusion tag, an approval, a maintenance window. Each one says which incident it prevents.
Dry runHow to preview it. Everything generated here is created enabled and applies when run; --dry-run previews.
UndoHow to reverse it — or an honest statement that you cannot, which is the more useful sentence.
Who is toldWhere the record goes when it acts. A run log nobody reads is not a record.

The checks run over that structure rather than over the generated YAML, so the tests can refuse an automation that is irreversible with no guardrail, or that changes something with no dry run, without reading a line of the output.

21. Common workflows

From an RVTools export to a VCF deployment spec

  1. VMware Inventory: import the RVTools .xlsx (and the collector JSON if you have it). Read the readiness and blockers.
  2. VCF Sizing: in From your estate, choose the management domain, host profile and domain split. Check the verdict.
  3. Continue in the spec builder: check the prefilled hosts and networks, choose the scenario, name the components, add host passwords. Save the settings.
  4. Download the SddcSpec, then validate it on the live installer.

Change a deployed VCF spec

  1. Data Editor: open the installer export (VCF-deployment-spec-….json).
  2. Edit fields in the form, or use Find and replace for a new subnet or domain. Watch the checks.
  3. Download, or Download without secrets to share it.

Rehost a cluster to a cloud

  1. Import the estate; on the inventory page, fix or note the blocked VMs.
  2. Multi-Cloud: Answer from the estate for the cluster, complete the rest, and save the recommendation as Word.
  3. Terraform: Rehost a cluster's VMs for the chosen cloud; Ansible: the inventory and before/after playbooks.

Build a landing zone or a migration as one project

  1. Terraform: add each piece to the build list — network first, then what sits on it. Use the ⇢ box to point each item at what the earlier ones create rather than typing ids.
  2. Name the stack, Generate stack, and download the files into one folder. terraform init, validate, plan.
  3. Ansible: build the matching site playbook the same way, for what has to be configured once the machines exist.
  4. Save both lists. That file is the design: load it to change one value and generate again.

Plan a portfolio of applications

  1. Migration → Portfolio: import the inventory CSV, which creates a draft row per application.
  2. Open each row, answer its ratings and hard constraints on the Intake and Ratings tabs, and evaluate. The row updates in place.
  3. Back on Portfolio, choose the wave planning mode and read the counts and the table.
  4. Export the portfolio as CSV for the programme, or as JSON to carry it to another browser.

23. Known limits

  • The spec builder's checks follow the documented 9.1 schema; the live VCF Installer's validation is the authority.
  • A deployment spec cannot yet be loaded into the spec builder's form; edit it in the Data Editor instead.
  • RVTools has no NVMe or NIC-speed data; those readiness columns show ? unless the collector's JSON is imported too.
  • A CSV import cannot answer the six ratings or the hard constraints, so its rows are drafts scored at the defaults until you open each one.
  • The portfolio lives in one browser on one machine. Export the JSON to move it anywhere else.
  • Multi-Cloud's Save as Word writes a Word-readable .doc (HTML), not a native .docx.
  • Editing YAML in the Data Editor's form drops comments; the Text view keeps them.
  • In a Terraform stack, a resource offers only its .id to other items, because that is the one attribute every resource has. Module items offer their real outputs. Anything else you write yourself.
  • An Ansible site playbook shares an answer only when two playbooks give it identically; anything named like a password is left out of group_vars/all.yml on purpose.
  • Network changes are written for the platforms listed and checked for structure, not simulated. Diff every one against the running configuration before it is applied.
  • The network vendor Ansible collections are unpinned and un-catalogued until npm run ansible:update runs on a connected machine.
  • Checks confirm names, structure and references. They do not confirm that a deployment will succeed in your environment.
